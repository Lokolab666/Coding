# S3 Bucket Configuration
For teams requiring an S3 bucket, below is the process for creating new buckets. See the following [video for a video explanation / walkthrough](https://medtronic.sharepoint.com/:v:/r/sites/WebDevModernization/Shared%20Documents/WebDev%20Cloud%20Solutions%20(Prometheus%20Argo%20Project)/Training%20Videos/Support/S3%20Bucket%20Creation.mp4?csf=1&web=1&e=Qyw0bP).

S3 buckets are always created through our Terraform projects. This ensures consistent setup that meets GCISO requirements.

## Prerequisites
Gather the following information from the team requesting the bucket:
1. Application Name
2. Cost Center
    * S3 bucket usage will be charged back to the application teams through Cost Centers. **Note: we need a cost center, not a WBS number.**
3. Does the application require Read / Write access to S3? Or Read-Only?
4. Is there existing data that needs to be transferred to S3?
    * What is the total size of the existing data?

## S3 Creation
1. Open the Terraform project
    * For DEV or TESTING environments: Open the [aws-it-argo-dev-mdt](https://code.medtronic.com/bcp_web/devops/infrastructure/terraform-deployments/aws-it-argo-dev-mdt) Terraform project.
    * For STAGING, RELEASE, or PRODUCTION environments: Open the [aws-it-argo-prod-mdt](https://code.medtronic.com/bcp_web/devops/infrastructure/terraform-deployments/aws-it-argo-prod-mdt) Terraform project.
2. Create a new branch for your changes.
3. Add a new file to the root of the project if one does not already exist for this application - named as `<appname>.tf`. We have one tf file per application to store all AWS objects associated to that application. If one already exists, simply add the S3 configurations to the existing file.
4. The S3 bucket setup consists of three objects:
    * S3 Bucket
        * The actual S3 bucket. Intelligent tiering is enabled by default to reduce costs for teams.
    * S3 Bucket IAM Policy
        * Provides which permissions are needed for the application - adjust this if the application only needs read access.
    * IAM Assumable Role for EKS
        * Team should run namespace for their application first, so we can restrict the S3 access by namespace(s) associated to this application.
    These objects can be copied from another existing `<appname>.tf` file that contains an S3, being careful to rename all objects.
5. S3 bucket object:
    * Replace `APP_NAME` and `app-name` everywhere with the app name.
    * Replace `env` with the application environment the bucket is for (dev, testing, staging, release, or production).
    * Ensure `CostCenter` contains the proper cost center value. This should be a numeric value
    * `bucket` value should contain the following format:
        * `mdt-` +
        * `app-name` +
        * `-env` (dev, testing, staging, release, or production) +
        * `-${local.aws_account_id}` - the account id for the account the bucket is created in
        * `-${var.region}` - the region the bucket is created in (default is us-east-1)

        ```terraform
        # ---------------------------------------------------------------------------
        # APP_NAME ENV S3 bucket
        # ---------------------------------------------------------------------------
        module "app_name_env_s3_bucket" {
        source = "git::https://code.medtronic.com/bcp_web/cloud-database-solutions/infrastructure/terraform-modules/mdt-cds-s3-bucket-module.git?ref=v1.1.4"

        create_bucket = true

        bucket = "mdt-app-name-env-389242548790-us-east-1"

        region      = var.region
        role_arn    = var.role_arn
        external_id = var.external_id

        owner_short_name = "mdt"
        owner_long_name  = "APP_NAME"

        sandbox = false

        tags = {
            Team       = "ACM IT"
            CostCenter = "510595"
        }

        intelligent_tiering = {
            general = {
            status = "Enabled"
            tiering = {
                ARCHIVE_ACCESS      = { days = 125 }
                DEEP_ARCHIVE_ACCESS = { days = 200 }
            }
            }
        }
        }
        ```


6. S3 IAM Policy object:
    * Replace `APP_NAME` and `app-name` everywhere with the app name.
    * Replace `env` / `ENV` with the application environment the bucket is for (dev, testing, staging, release, or production).
    * Update `description` to refer to the correct application and permissions needed
    * Update the `policy` json object if needed to prevent Put / Delete permissions if the application needs read-only access.
    * Update all `Resource` sections to reference the correct module / bucket created in Step 5.

    ```terraform
    # ---------------------------------------------------------------------------
    # IAM Policy for APP_NAME S3 bucket
    # ---------------------------------------------------------------------------
    resource "aws_iam_policy" "app_name_env_s3_policy" {
    name        = "app-name-env-s3-policy"
    description = "APP_NAME ENV S3 read/write + KMS decrypt"

    #checkov:skip=CKV_AWS_355
    policy = jsonencode({
        Version = "2012-10-17"
        Statement = [
        {
            Effect = "Allow"
            Action = [
            "s3:GetObject",
            "s3:PutObject",
            "s3:DeleteObject",
            "s3:ListBucket",
            ]
            Resource = [
            module.acm_strat_alliance_dev_s3_bucket.s3_bucket_arn,
            "${module.acm_strat_alliance_dev_s3_bucket.s3_bucket_arn}/*",
            ]
        },
        {
            Effect = "Allow"
            Action = [
            "kms:Decrypt",
            "kms:ReEncrypt*",
            "kms:GenerateDataKey*",
            "kms:Encrypt",
            "kms:DescribeKey",
            ]
            Resource = [
            module.acm_strat_alliance_dev_s3_bucket.s3_bucket_kms_arn,
            ]
        }
        ]
    })
    }
    ```

7. IAM Assumable Role for EKS:
    * Update `role_name` value with `app_name` and `env`. Leave the `${var.obj_prefix}` prefix and `eks_role` suffix, for naming standardization.
    * Update `provider_url` depending on which cluster the role will be used with:
        * Argo Dev Cluster:  `data.aws_eks_cluster.argo_dev_eks_cluster.identity[0].oidc[0].issuer`
        * Argo Quarantine Prd Cluster: `data.aws_eks_cluster.argo_quarantine_eks_cluster.identity[0].oidc[0].issuer`
        * Argo Prd Cluster: `data.aws_eks_cluster.argo_prod_eks_cluster.identity[0].oidc[0].issuer`
    * Update `oidc_subjects_with_wildcards` with the namespace(s) that need access to this S3 bucket. The value needs to be in the format of `system:serviceaccount:<namespace>:default` - where namespace can be a partial or full value. If partial, use `*` characters as wildcards.

    ```terraform
    # ---------------------------------------------------------------------------
    # IAM Role for EKS service-account to assume and access APP_NAME ENV S3
    # ---------------------------------------------------------------------------
    module "app_name_env_for_eks_s3" {
    source  = "terraform-aws-modules/iam/aws//modules/iam-assumable-role-with-oidc"
    version = "5.59.0"

    aws_account_id        = local.aws_account_id
    role_name             = "${var.obj_prefix}_app_name_env_eks_role"
    create_role           = true
    force_detach_policies = true

    provider_url = data.aws_eks_cluster.argo_dev_eks_cluster.identity[0].oidc[0].issuer
    role_policy_arns = [
        aws_iam_policy.acm_strat_alliance_dev_s3_policy.arn,
    ]

    # restrict to your app’s namespace(s) once known
    oidc_subjects_with_wildcards = [
        "system:serviceaccount:argo-acm-strat-alliance-*:default",
    ]
    }
    ```
8. Commit changes to the branch and confirm successful pipeline run through the build stage.
9. Merge to main
10. Press `Play` on the deploy job.
11. Confirm S3 exists by logging into the AWS account and navigating to S3.
12. Provide the following information to the application team:
    * The S3 Bucket name: (i.e. `mdt-app-name-env-awsaccountid-us-east-1)
    * The EKS role_name: (i.e. TF-argo_app_name_env_eks_role)
        * The application team will need to add this as the [`awsIAMRoleName`](https://playbook.argo-dev.eks.mdtcloud.io/build-and-deploy/settings/example_environmentinfo_json/#awsiamrolename) in the `environmentInfo.json` file for the applicable environment. If this is not added, their application will not have permissions to read/write to the S3 bucket.

## App Team AWS Access ##
To provision access to the Argo account for team S3 access follow the below steps to provision that access. This can be useful for teams to be able to see their bucket and also get AWS credentials for use locally for testing.

1. Submit a ServiceNow ticket to Cloud-Global with the following details:
* Ask them to create a permission set role & associated AD group
* Provide what rights are needed and provide to them. Any future changes also need to be managed through the Cloud team.
```text
Please setup a new SSO role and associated AD group for ACM Strat Alliance App Users in it-argo-dev-mdt (#389242548790) account and assign the below users to this role.

New Role Name: ACM-Strat-Alliance-App-Role

Attach the following existing policies (or replicate the policy permissions) in the account to the permission set for this new SSO role:
acm-strat-alliance-dev-s3-policy
ViewOnlyAccess

Add the following users to the role:
Montebello, Ash (montea4)
Kumar, Podili (kumarp133)
```
2. Await fulfillment from the Cloud-Global team. Once complete, confirm that user is able to:
   * Access [AWS start screen](https://medtronicsso.awsapps.com/start/)
   * Sees the AWS account and the newly created role
   * Is able to access the AWS account through clicking the role, and has access to the appropriate objects within the account.
