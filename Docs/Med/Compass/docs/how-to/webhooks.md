# Webhooks

Use this guide to configure application-specific Git webhooks for Flux while reusing the platform-managed webhook hostname and certificate.

The Compass onboarding template (`semantic-release/flux-registration.yml`) now includes webhook receiver creation as part of standard app registration.

## Standard Pattern (Recommended)

Use one shared external webhook ingress per cluster, and create a separate Flux `Receiver` per application:

- **Shared per cluster:** hostname, ALB, certificate ARN, WAF ARN
- **Per application:** `Receiver`, webhook token secret, GitLab webhook endpoint URL

This gives every app a unique hook endpoint without creating additional hostnames/certificates.

For multi-environment apps, use **one receiver per app per cluster** (not one receiver per environment). The receiver targets all app GitRepository sources through labels.

---

## Ownership Model

### Platform/GitOps Team

- Maintains shared webhook ingress in `flux-gitops` (hostname/cert/WAF)
- Keeps ingress endpoint stable for the cluster
- Reviews and merges receiver onboarding changes

### Client Team (App Team)

- Adds an app-specific Flux `Receiver`
- Stores/references the webhook token secret
- Configures the webhook in the app repo (GitLab)

## Suggested Repo Structure

Yes — app-specific receivers can (and should) live with the app in the cluster apps tree.

Example for `einstein` in `TF-argo-dev`:

```text
flux-gitops/
  clusters/
    TF-argo-dev/
      infrastructure/
        flux-webhook/
          kustomization.yaml                   # shared ingress/host/cert/WAF only
      apps/
        <app-path>/
          einstein-webhook.yaml                # app receiver (generated by onboarding)
          einstein-source-dev.yaml
          einstein-source-testing.yaml
          einstein-source-staging.yaml
          einstein-source-production.yaml
          kustomization.yaml
```

This keeps app-owned resources with the app while platform-owned ingress remains under `infrastructure/flux-webhook`.

## Einstein Example

### 1) Add an app-specific Receiver (in `flux-gitops`)

If you use the standard onboarding job, this receiver is generated automatically as `${APP_NAME}-webhook.yaml` in `clusters/<cluster>/apps/<app-path>/`.

```yaml
apiVersion: notification.toolkit.fluxcd.io/v1
kind: Receiver
metadata:
  name: einstein-webhook
  namespace: flux-system
spec:
  type: gitlab
  events:
    - "Push Hook"
    - "Tag Push Hook"
  secretRef:
    name: einstein-webhook-token
  resources:
    - apiVersion: source.toolkit.fluxcd.io/v1
      kind: GitRepository
      name: '*'
      matchLabels:
        app: einstein
        webhook: enabled
```

### 2) Ensure token Secret exists

Use your standard secret workflow (for example SOPS + Flux) for the webhook secret in namespace `flux-system`.

By default, onboarding generates and references `<app>-webhook-token` (for example `einstein-webhook-token`).

The secret key expected by Flux Receiver is:

```yaml
data:
  token: <base64-encoded-app-specific-random-token>
```

Token generation/update rules:

- The token can be any sufficiently random string.
- You can generate one with: https://it-tools.tech/token-generator
- In Kubernetes Secret `data.token`, store the Base64-encoded value of that random string.
- In GitLab `Settings -> Webhooks -> Secret token`, paste the same token in plain text (not Base64).
- The webhook token must match between GitLab and the Flux Receiver secret or delivery will fail with 401/403.

Example (PowerShell):

```powershell
$raw = "replace-with-random-token"
[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($raw))
```

### 3) Get the endpoint path generated by Flux

After the receiver is applied, retrieve its webhook path:

```bash
kubectl -n flux-system get receiver einstein-webhook -o jsonpath='{.status.webhookPath}'
```

Build the final URL using the already-configured shared webhook host for that cluster:

```text
https://<shared-webhook-hostname><webhookPath>
```

Example:

```text
https://flux-webhook-ext.argo-dev.eks.mdtcloud.io/hook/...
```

When using `.flux-verify-env`, the job emits:

- `FLUX_WEBHOOK_PATH`
- `FLUX_WEBHOOK_URL` (when `FLUX_WEBHOOK_BASE_URL` is set)

as dotenv artifacts in `flux-verify.env`.

### 4) Configure the GitLab webhook (in `einstein` repo)

**Where:** `Settings → Webhooks`

You need a **separate webhook for each cluster** your application deploys to (dev, staging, production, etc.).

**Naming convention:**
```
compass-flux-{cluster-name}
```
Examples: `compass-flux-tf-argo-dev`, `compass-flux-tf-argo-prd`

**Webhook URL:** app-specific URL from step 3

**Secret token:** same raw token value used to build the Kubernetes Secret `data.token` (before Base64 encoding)

**Trigger events — select both:**
- ✅ Push events
- ✅ Tag push events

**For Push events, filter by branch using a regular expression:**

In the Push events section, enable **Wildcard/Regex Push events** and set a pattern matching the branches that deploy to that cluster:

```
^(dev|testing)$
```

Adjust per cluster:
- **Dev cluster:** `^(dev|testing)$`
- **Production cluster:** `^(staging|release|production)$`

**SSL verification:** Leave **Enable SSL verification** checked.

**Test the webhook:** After saving, use the **Test** dropdown on the Webhooks page and select **Push events**. A successful response shows:

```
Hook executed successfully: HTTP 200
```

## Conventions

- Receiver manifest location: `clusters/<cluster>/apps/<app-path>/<app>-webhook.yaml`
- Receiver name: `<app>-webhook` (standard template)
- Secret name (default): `<app>-webhook-token`
- One receiver per app per cluster (covers all env sources for that app in that cluster)
- Keep shared ingress host/cert unchanged unless platform team directs otherwise

## Optional Full Automation (GitLab API)

You can auto-create or auto-update the app project's GitLab webhook from `.flux-verify-env`.

Set these CI variables:

- `AUTO_CONFIGURE_GITLAB_WEBHOOK=true`
- `GITLAB_WEBHOOK_API_TOKEN=<token with API scope on app project>`
- `FLUX_WEBHOOK_BASE_URL=https://<shared-webhook-hostname>`
- `WEBHOOK_SHARED_TOKEN=<optional override; normally read from flux-system/<app>-webhook-token>`
- `GITLAB_WEBHOOK_BRANCH_FILTER_REGEX=<optional override, default derived from cluster>`
- `GITLAB_WEBHOOK_ENABLE_SSL_VERIFICATION=true` (default)

Behavior:

- If a hook already exists for the computed URL, it is updated.
- If no hook exists, it is created.
- Push events are filtered to cluster-appropriate branches by default (for example dev cluster uses `^(dev|testing)$`).
- Push and tag events are enabled.
- A best-effort API test is attempted for push/tag events after create/update.

## Validation Checklist

- Receiver is Ready:

```bash
kubectl -n flux-system get receiver einstein-webhook
```

- Webhook path is populated:

```bash
kubectl -n flux-system get receiver einstein-webhook -o jsonpath='{.status.webhookPath}'
```

- Push to `einstein` triggers source refresh/reconcile:

```bash
kubectl -n flux-system logs deploy/notification-controller --since=10m | grep -i einstein
```

## Troubleshooting

- **HTTP 404 from webhook URL:** wrong path; re-check `.status.webhookPath`
- **HTTP 401/403:** token mismatch between GitLab and Kubernetes Secret
- **No reconcile observed:** verify `resources` points to the correct `GitRepository` name/namespace
- **Wrong cluster updates:** confirm cluster-specific webhook hostname was used
