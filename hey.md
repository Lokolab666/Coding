While activating the testing environment for ciam/cic-profilemanagement (Compass CI, cluster TF-argo-dev), Terraform Plan in bcp_web/devops/infrastructure/terraform-deployments/aws-it-argo-dev-mdt fails with a duplicate variable declaration, blocking the certificate MR for the testing hostname. Root cause analysis was done by Sravan Kumar Podili (thread on DL IT Argo Core Team, 8/27–8/28); the application team has confirmed which configuration is authoritative. This incident tracks the agreed platform-side cleanup.

Error
Duplicate variable declaration: ciam_cic_profilemanagement_sops_key_value
  Already declared at: app_ciam_cic-profilemanagement.tf:284
  Declared again at:  app_ciam_cic-profilemanagement.tf:521

Root cause
MR !249 (merged; "Onboard ciam/cic-profilemanagement: SOPS + IRSA TF resources", generated by the self-service onboarding automation) appended an APP_BASELINE block to app_ciam_cic-profilemanagement.tf. The file already carried a pre-existing SOPS configuration for this application from the dev-environment era, and it lacked the AUTOGEN markers the template checks for, so the generated block duplicated the SOPS variable/secret/secret-version. Every subsequent Terraform Plan on main fails, including MR !250 (testing certificate), which introduces no SOPS resources itself.

Agreed resolution (per the email thread)
1. Authoritative config (KEEP): the pre-existing block around line 284 — aws_secretsmanager_secret "sops_age_key_ciam_cic_profilemanagement" plus its variable and secret-version, managing compass-ci/ciam/cic-profilemanagement/sops-age-key. This entry is decrypted daily by the dev environment and is the same path the testing onboarding (flux-gitops !47) references. One SOPS config serves the application's environments in this account.
2. REMOVE: the SOPS portion of the generated APP_BASELINE block (~lines 521–529): the second variable declaration, aws_secretsmanager_secret "sops_age_key_cic_profilemanagement", and its secret-version. Never applied (Plan has failed since merge), so removal is expected to change no real infrastructure.
3. IRSA portion of APP_BASELINE (cic_profilemanagement-nonprod-secrets-policy, eks_oidc_nonprod_cic_profilemanagement): retain per platform judgment — resource names are new/non-duplicated and appear to be the standard per-app baseline.
4. GUARDRAIL: post-cleanup Plan must show NO changes to existing Secrets Manager resources (no new secret versions) — only the ACM/Route53 certificate additions from !250. The live secret value is depended on daily by dev and imminently by testing.
5. Re-run Terraform Plan for !250; on a clean plan, review and apply; the application team then re-runs the provision-cert-testing CI job to stamp the certificate ARN onto the testing ingress.
6. flux-gitops !47 ("Onboard profilemanagement [testing]") is independent of this issue and can proceed in parallel.
